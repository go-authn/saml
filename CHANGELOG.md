# Changelog

## v0.8.0

- `Description` gains optional `Organization` (saml-metadata-2.0-os 2.3.2.1),
  `Contacts` (2.3.2.2, with the REFEDS security-contact marker), `Logos`
  (`mdui:Logo`, width and height required) and the per-language
  `InformationURLs` and `PrivacyStatementURLs`. `Organization` and the
  `ContactPerson`s are written after the `SPSSODescriptor`, as the schema's
  sequence requires.
- `Description.Validate` refuses what a federation would: URLs that are not
  https, a logo without a positive width and height, an unknown contact type, an
  address that is not a bare one, a language given twice, an incomplete
  Organization. `SP.Metadata` calls it; so can a caller reading its
  configuration at start.
- With none of the new fields set the bytes are those of v0.7.3
  (`TestMetadataGoldenWithoutNewBlocks`, golden files generated by v0.7.3).
  The output is validated against the OASIS metadata and mdui schemas by
  xmllint (`testdata/xsd`, the published schemas unmodified; skipped where
  xmllint is absent, a failure with `SAML_REQUIRE_JUDGE=1`).

## v0.7.3

- The loopback rule and the redirect policy of `Federation` come from
  `github.com/go-authn/harden/redirect`, shared with oidc, rp, awscred and
  wireguard. Loopback now also means `*.localhost`, in any letter case and with
  a trailing dot; an IPv6 zone such as `::1%eth0` is no longer loopback; the
  redirect error names the scheme and host only.

## v0.7.2

Two fixes from the 2026-11-21 security audit. Neither refuses anything a
conforming IdP sends, hence a patch release: the only signature layout newly
refused is one that no IdP produces (see below), and
`TestASignatureOnBothTheResponseAndTheAssertionStaysAccepted` pins that a
Response and its Assertion both signed with RSA-SHA256 (ADFS, Okta, Shibboleth
by option) is still accepted.

- Fixed: the signature-algorithm allow-list looked only at the direct
  `ds:Signature` children of the Response or Assertion, while goxmldsig
  verifies the first signature in document order, at any depth, that
  references the element. A SHA-1 signature nested under `<Extensions>`, next
  to an allow-listed decoy signature, passed the allow-list. A signature that
  references the element being verified and is not its direct child is now
  refused. A signature on the Assertion inside the Response references the
  Assertion's ID, so it is not affected. Placing the decoy takes the signer
  or a SHA-1 collision; this is not a bypass for an outsider.
- Fixed: the replay-cache entry of a Response lasted until the first bearer
  SubjectConfirmation's `NotOnOrAfter`, while the Response stays acceptable
  until the latest confirmation that still holds. A second confirmation with a
  later deadline let the same Response be delivered again after the entry was
  evicted (saml-profiles 4.1.4.5). The entry now lasts as long as the Response
  can be accepted, including the clock skew.

## v0.7.1

- Fixed: `Federation` treated any DNS name starting with `127.` as loopback
  (`127.evil.example`), which let it fetch metadata over cleartext http and
  follow an https to http redirect to such a host. Loopback is now `localhost`
  or an IP literal that is loopback (`127.0.0.0/8`, `::1`).

## v0.7.0

- Added to `samltest.Assertion` (#28), for an SP's tests that until now had to
  build these responses with xmlsec1. A zero value writes what v0.6.1 wrote.
  - `Status`: the StatusCode and its nested codes (`Responder` then
    `NoPassive`, for a refused passive login). A Response whose top-level code
    is not Success carries no assertion, encrypted or not.
  - `Subject`: the Subject's NameID in full (`samltest.NameID`: value, format,
    NameQualifier, SPNameQualifier), in place of the transient `NameID`
    string; setting both is refused.
  - `AuthnInstant`: when the IdP says the person authenticated, apart from
    `Now`, so the authentication moves without moving the validity window.
- Added: `samltest.Attribute.NameIDs`, values that are a `saml:NameID`
  element (eduPersonTargetedID as a Shibboleth IdP releases it).
- Each shape is read back by this module's SP, and verified and decrypted by
  xmlsec1 (`TestResponseOptions`, `TestJudgedByXMLSec1`). Without xmlsec1, a
  planted fault (a refusal that keeps its assertion) still turns
  `TestResponseOptions` red.

## v0.6.1

- Added: fuzz targets next to the parser (#21). `FuzzAccept` (a response the
  fuzzer rearranged is refused, or says exactly what the IdP signed; seeded
  with a signed assertion in the clear, a signed Response around an encrypted
  one, and the signature-wrapping layouts XSW1-8), `FuzzParseMetadata`,
  `FuzzDecrypt` (GCM and CBC, the EncryptedKey inside EncryptedData's KeyInfo
  and beside it; CBC is never opened unauthenticated, and what GCM opens is
  what was sealed) and `FuzzLimits` (`limits.check` and `parse` agree on what
  is refused, and `check` allocates in proportion to its input). Seeds come
  from `samltest`; the corpus is committed under `testdata/fuzz` and replayed
  by every `go test`. A planted fault (the CBC gate removed) turns
  `FuzzDecrypt` red from its seeds alone.
- Fuzzed, 130 s each, 16 workers, on one machine at load > 8 (executions, not
  times, are the measure): `FuzzAccept` 1,502,094; `FuzzParseMetadata`
  2,120,800; `FuzzDecrypt` 5,146,715; `FuzzLimits` 1,119,772. No crash, hang or
  property violation was found.
- Added: `TestHostileInputsAreRefusedCheaply`. Under a soft memory limit, an
  entity-expansion bomb (billion laughs), an external entity, 80,000 and
  1,048,576 levels of nesting, 60,000 sibling elements, a 150 KiB CipherValue,
  a response over the cap and an all-whitespace one are each REFUSED, with
  `TotalAlloc` bounded (4 to 8 MiB).
- CI: a `fuzz` job runs each target for 30 s on every push and pull request,
  and keeps the input that broke one as an artifact. (go-authn/kdc and
  go-authn/ldap have no fuzz step; they replay their corpus in `go test`, which
  this repository does too.)
